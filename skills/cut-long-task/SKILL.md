# 长任务分段

在“任务收尾闹钟”的同对话一次性续做方式上增加额度保护：默认立即推进当前长任务；五小时剩余额度达到用户设定的保留比例时主动收尾，等下一个指定时间点再检查和续做。本技能自包含，无需同时安装或调用 `task-finish-clock`。

## 输入与任务绑定

- 绑定本次调用附带的主任务，或本对话最近一个明确的实质性任务，生成稳定任务标识。保存目标、验收标准、工作目录、产物路径和原授权；不要把创建分段计划本身误当主任务。任务不唯一时先澄清。
- 接收一个或多个恢复时间点，以及可选的**剩余额度保留比例** `T`。`20%`、`0.2`、`0.20` 等价；省略比例时使用 `T=0.2`。先解析带日期/时分的时间表达，再解析独立的比例参数，不把日期、钟点或主任务中的百分比当成阈值。
- 小数须在 `[0,1]`，百分比须在 `[0%,100%]`；裸值 `20`、负数、越界值或相互冲突的多个比例先澄清，不擅自纠正。`0` 表示无保留缓冲、读到 0% 才暂停；`1` 表示立即暂停、不启动实质工作。
- 把时间点转换成当前环境时区中的绝对时间；用户明确时区优先，环境无时区才询问。相对时间以本次调用为基准，恢复时不重新计算。去重并排序；无日期钟点取下一次出现，有歧义、已经过去或等于当前时刻的时间需澄清。
- 至少需要一个可验证的未来恢复时间点。缺少时间或比例无效时，不创建不完整计划，不启动新的高消耗阶段；先做必要的进度保存，再询问最少的缺失信息。
- 除非用户明确说“先暂停”“到点再开始”，默认立即执行并同时建立恢复计划。明确延迟启动时，只保存任务快照和计划，不提前开始主任务。

例：`$cut-long-task 今晚 21:00、明天 09:00，保留 20%`；`$cut-long-task 明天 09:00，0.3`；`$cut-long-task 明天 09:00`（默认保留 20%）。

## 真实额度与能力检查

开始或恢复前发现并调用真实的额度读取工具，例如 Codex 桌面端 `get_usage_limits`。优先读取 `rateLimitsByLimitId`，旧环境才用 `rateLimits`；检查适用于当前任务/模型的额度桶中的各窗口，按 `windowDurationMins=300` 识别五小时窗口，不能仅凭 `primary`、`secondary` 字段名猜测。多个相关五小时窗口同时限制当前任务时，以最小剩余比例控制；不混入无关模型或 Code Review 的独立额度桶。无法确定适用桶时报告该缺失。

对有效窗口计算 `R=clamp(100-usedPercent,0,100)/100`。`usedPercent` 是已用百分比；暂停条件为 **`R <= T`**，只有 **`R > T`** 才可开始下一工作单元。记录观测时间、桶标识、窗口长度和 `resetsAt`（Unix 秒），不要用已工作几小时、token 数、上下文占用或距重置的时长推算剩余额度。缺失/null/非数字读数不是 0 或 100。

每次恢复都重新读取额度，不能因为时间已到、过去五小时或 `resetsAt` 已过就假定额度恢复。周额度耗尽、服务器报告当前任务不可用等实际硬限制也会阻止续做；不要将同一保留比例套到周额度上。

若工具缺失、调用失败、没有可验证的五小时窗口或数据仍过期，保存状态并明确“额度保护未能验证，当前保持暂停”；只保留已获授权且可验证的恢复时间点。不要静默降级成无额度保护的长任务。环境明确不设五小时额度时说明此模式不适用，是否改用其他方式由用户决定。

这是协作式分段控制，不是服务端硬限额。额度在同账号的任务/设备间共享；两次观测之间、收尾、工具调用和其他并行任务都可能继续耗用额度。启用时用一句话说明按检查点尽力预留，不能保证精确停在阈值。不得因此暂停其他无关任务、变更模型/套餐、购买额度或消耗额度重置券。

## 尽早建立一次性恢复计划

在可能耗用大量额度的工作前，先建立初始检查点，再为每个用户时间点创建**当前对话内的一次性 heartbeat**。只有用户确实要求运行此分段计划时才创建；创建/编辑本技能本身不启动任何恢复任务。

使用当前环境的自动化工具（例如 `automation_update`），名称为 `长任务分段 · <任务标识> · <月日时分>`，目标为当前 thread，每项只运行一次（例如 `COUNT=1`）。保持同一工作目录与产物，不新开对话，不创建 cron 独立任务，不增加周期性额度监控或用户未指定的恢复时间。机器需在线且客户端运行时才能执行本地恢复，应在首次启用时简短告知。

创建前查找既有自动化，幂等键为“当前线程 + 同一稳定任务标识 + 同一绝对时间 + cut-long-task”。完全匹配的 `ACTIVE` 项复用；阈值或提示词变更用原 ID 更新。改期先定位原 ID，找不到或候选不唯一时询问，不退化成新建，不改动其他技能/任务的计划。

每项创建/更新后独立查看，确认 `ACTIVE`、heartbeat、当前 thread、单次、绝对时间及时区、任务快照和阈值正确。把 ID 和验证状态写入检查点；失败的项目不算已安排。全部失败时保存进度、报告无法自动恢复并暂停，不宣称计划生效；部分成功时明确失败项，按已确认项运行。

每个持久提示词须包含：稳定任务标识、原任务目标和验收条件、范围/权限、绝对恢复时间表和阈值、工作目录/产物、检查点绝对路径（无文件时嵌入最小进度快照），以及本技能和相关 `AGENTS.md`/技能的路径。采用以下语义，并允许读取其他已确认的本任务计划，不能依赖仅存在于内存的前次状态：

> 这是 cut-long-task 对同一长任务的一次性恢复检查。先读最新对话、检查点、适用 AGENTS.md 和技能，服从后来修改或授权撤销。先以产物和真实外部状态核验完成；已完成则完全静默且不重复执行。若本次恢复轮之外已有同任务执行者正在推进，本次只退出，不并行启动第二个执行者，也不把本次机会预留为稍后运行；本次恢复自身造成的线程 running 状态不算另一执行者。否则重新读取适用的五小时真实剩余额度；R <= T 时保持暂停，R > T 且不存在其他硬性限制时，接续本任务，执行每单元前后检查、持续保存、触阈值主动收尾的同一规则。读数不可验证时保持暂停，不假设额度足够。不自行新增或改期恢复任务。本次时间点只消费一次；需要用户选择/权限或最后一个时间点仍无法推进时仅通知一次；状态未变化且尚有后续时间点时静默。续做产生有意义的完成结果才报告结果。

如果同任务同时已有 `task-finish-clock` 等旧续做计划，识别会绕过额度保护的冲突。仅在用户已授权替换/统一该任务计划时更新那些精确匹配项；否则说明冲突，不声称所有入口都受保护，不擅自删除其他计划。

## 执行与分段收尾

1. 以可独立保存、可重入的小单元推进任务。**每个单元开始前、完成后，以及启动高消耗工具或派生代理前读取额度**；持续长阶段在可交还控制权处至少约每五分钟再查一次，临近阈值时进一步缩短单元和检查间隔。不要把大批工作合并成一次不可观测的调用。工具执行中或模型持续生成时无法异步打断，不能声称实时监控或精确中断；先拆小工作并持续留下进度。
2. `R > T` 且任务未完成时继续；建立自动化的确认作为中间进度，不得据此结束本轮。即使跨越了额度重置，也以新读数继续执行相同规则。
3. `R <= T`、额度不可验证或硬限制出现时，**停止领取新工作**，只完成避免损坏所需的最小动作，保存可恢复状态。不得以“快做完了”为由继续跑大测试、润色或扩大验证来耗用保留额度，也不为等重置而在当前轮长时间睡眠/轮询。
4. 派发时向本任务派生代理同步分段约束，让其完成小单元后及时交还控制。收尾覆盖本任务派生的所有代理与耗用模型额度的后台工作：停止派发，要求保存进度并暂停；仍在运行的用可用的协作控制停止本任务的派生执行者。记录已完成和未完成工作。不要影响用户的其他任务。已运行的不耗模型额度且安全可留的本地进程可继续，记录进程/会话标识与查询方法；不得结束可能损坏数据的进程来强求卡点。
5. 使用 [references/checkpoint.md](references/checkpoint.md) 在任务工作目录中创建或更新本任务独享的检查点。默认放在 `.cut-long-task/<线程与任务的安全标识>/state.md`，避免覆盖其他任务；无法写文件时在本对话与持久提示词中保存最小快照并说明限制。不要复制秘密或整段对话。
6. 选出**收尾完成时刻之后**最早的已确认、尚未消费的用户时间点。当前轮结束，让调度器到点恢复；不可在主动暂停后继续同一长任务。首次阈值暂停简短告知已保存进度、当时读数和下次绝对恢复时间。已经消费或在执行期间过去的时间点不补跑、不滚动到明天。

恢复时先核验本次恢复轮之外是否已有本任务的执行者；排除本次恢复自身造成的 `running` 状态，串行继承或复用原执行，不能只凭陈旧的状态文本就永远退出。用当前线程/代理/进程的可验证状态消歧。重试外部操作前先核对实际结果，防止重复发信、重复提交或覆盖用户修改。相关旧任务权限不会因换到恢复轮而扩大。

## 结束和通知

- **真正完成**：按用户验收要求核验产物、测试或外部状态，标记 `completed`；本轮新增完成成果简短交付。后续既定检查读到已完成时完全静默，不重复工作；静默仍可能留下产品运行记录。
- **额度不足但尚有未来时间点**：保持暂停；如果只是重复同一暂停状态，静默等待下一项。额度恢复后由下一次实际检查重新决定能否继续。
- **没有已确认的未来时间点**（包括最后一次恢复仍低于阈值、时间已过、计划被取消或运行时耗尽了时间表）：保存最新检查点，标记 `needs_time`，一次性告知需要补充时间。不要自建循环、用重置时间自动改期、补造时间点，或在旧时间点过期后声称仍有自动恢复。
- **需要用户输入、权限、实际失败或能力缺失**：只报告最小阻塞及用户需要做的动作。持续相同阻塞且仍有后续检查时不重复提醒；用户取消任务或撤销授权后不再续做。

首次启用简洁确认任务、保留比例、各绝对恢复时间与时区、创建结果，以及当前立即执行/已暂停/延迟启动状态；不展示原始 RRULE 或整段自动化提示词。仅创建技能时只交付技能和用法，不虚构已经启用的监控或恢复任务。
